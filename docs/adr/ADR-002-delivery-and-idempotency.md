# ADR-002：至少一次投递与 Elasticsearch 幂等写入

- 状态：已接受
- 日期：2026-07-30
- 更新日期：2026-08-03

## 背景

Filebeat 和 Kafka 消费者在恢复时可能重复投递事件。Elasticsearch
写入也可能已经成功，但客户端没有收到响应。因此，单次测试中未观察到重复，
不能作为系统具备恰好一次语义的依据。

处理器需要确定性的事件标识、明确的确认边界和毒消息处理路径，使恢复过程
既不会产生重复文档，也不会永久阻塞分区。

## 决策

### 投递保证

该管道采用**至少一次**投递，不声明不受限制的恰好一次投递。正确性以声明的
测试窗口和资源边界内，逻辑唯一输入数与 Elasticsearch 唯一文档数的对比来
衡量。

### 确定性事件 ID

`event_id` 版本 1 严格按以下顺序使用字段：

1. `kubernetes.pod.uid`
2. `container.id`
3. `log.file.path`
4. `log.offset` 的十进制文本
5. 规范化为 UTC RFC3339Nano 的 `@timestamp`
6. 原始 `message`

将 UTF-8 值编码为版本前缀，后接带长度前缀的字段：

```text
v1|<byte-length>:<value><byte-length>:<value>...
```

对这些字节计算 SHA-256，并呈现为：

```text
sha256:<lowercase-hex>
```

长度前缀可防止值中的分隔符改变字段边界。Kubernetes 元数据已失效的采集事件
保留在 `logs.unclassified`，不进入正常处理器，因此不以路径指纹冒充本业务
`event_id` 所需的 Pod UID。缺失必需的标识字段属于永久性校验
错误；处理器不得自行生成随机替代值。

### Elasticsearch 写入

- 将计算值写入文档的 `event_id` 字段，并使用同一个值作为 Elasticsearch
  文档 `_id`。
- 使用批量 `create`，不得使用 `index` 或自动生成的标识。
- 成功创建后，将该记录视为已处理。
- 同一 `_id` 的批量单项级 HTTP 409 表示已确认的重复事件；增加重复计数，
  并将该记录视为已处理。
- 必须逐项处理批量结果；不能因批次的 HTTP 响应成功而隐藏其中某一项的
  失败。

### Kafka 确认

- Filebeat 从 Kafka 收到的生产者确认，与 `log-processor` 的消费者
  偏移量提交是两个独立边界。生产者和消费者都不得将“即发即弃”视为成功。
- Filebeat 写入业务主题，以及处理器写入死信队列，都必须获得等价于
  `acks=all` 的 Kafka 服务节点确认。当副本因子为 1 时，这只能确认本地
  服务节点，不代表高可用保证。
- 禁用自动偏移量提交。
- 记录只有满足以下任一条件后才可提交：
  1. Elasticsearch 已创建该记录；
  2. Elasticsearch 通过 HTTP 409 确认该记录已存在；或者
  3. 其永久性失败已成功写入被接受的死信队列路径。
- 每个分区只能提交已连续处理的最高偏移量，不能越过更早且尚未解决的
  记录进行提交。
- 发生重平衡或崩溃时，未完成的偏移量保持未提交状态，并允许被重新投递。
- 优雅停止时，先停止拉取，完成或取消有界的处理中任务，只提交已连续完成的
  偏移量，然后退出。

### 重试分类

网络超时和 Elasticsearch 的暂时性响应（例如 429、502、503 和 504）需要
重试，且不得提交偏移量。每个投递周期最多尝试 6 次，初始等待 250 ms，
每次翻倍，最大为 4 s，并采用全抖动；取消信号必须能中断等待。

投递周期耗尽后，不得丢弃记录、写入死信队列或确认记录。暂停受影响的分区，
暴露未就绪状态，并保留偏移量以便恢复或重新投递。只有依赖健康检查恢复，
或处理器重启后，才开始新的投递周期。对于已丢失响应的请求，使用
`create` 重试是安全的；如果第一次请求实际已经成功，重试将通过 HTTP 409
收敛。

身份验证或授权失败属于配置故障，会使处理器进入未就绪状态。模板缺失、映射
冲突和集群阻塞也属于系统性故障：停止推进且不提交。无效 JSON、缺失必需
字段，以及单条记录的值违反已经验证的映射，属于
永久性记录故障。

### 毒消息

初始永久性失败路径是 Kafka 主题 `logs.dlq`，包含一个分区，副本因子为 1。
死信队列记录包含：

- 原始源主题、分区和偏移量；
- 错误类别和安全的错误摘要；
- 尝试次数；
- 存在时的 `test_run_id`；
- 遵守同一本地数据与密钥规则的原始载荷。

只有死信队列写入成功后，源偏移量才可提交。如果死信队列写入失败，源记录保持
未解决状态。正常业务消费者不订阅 `logs.dlq`。

## 后果

### 正面影响

- 重复投递会收敛为一个 Elasticsearch 文档。
- 偏移量推进代表已经得到持久化结果或持久化的失败证据。
- 部分批量写入失败和毒消息均可观测。
- 事件 ID 算法可独立进行单元测试，并具有版本。

### 负面影响

- Elasticsearch 暂时不可用时，可能暂停某个分区的处理。
- 死信队列的运维和保留策略会增加配置与测试工作。
- 更改标识字段或编码方式时，需要新的 ID 版本和迁移决策。
- 至少一次 Kafka 流量中仍可能存在重复的物理记录。

## 已拒绝的替代方案

- **由 Elasticsearch 自动生成 ID：**重复投递会产生重复文档。
- **处理时生成随机 UUID：**同一个源事件重试后会得到不同的 ID。
- **在写入 Elasticsearch 前提交 Kafka：**处理器崩溃后可能丢失事件。
- **对每种错误无限重试：**一条无效事件可能永久阻塞分区。
- **将每种失败都写入死信队列：**这会把基础设施故障掩盖成错误数据。
- **声明恰好一次：**Filebeat、Kafka 和 Elasticsearch 之间的故障边界不
  支持该声明。

## 验证义务

- 同一个规范输入始终产生相同的 `event_id`。
- 任一标识字段发生变化时，都会产生不同的 ID。
- 包含分隔符的字段值不会发生碰撞。
- 重复投递只产生一个 Elasticsearch 文档和一次重复观测。
- Elasticsearch 成功后丢失响应或提交时会触发重试；随后由 HTTP 409 结束
  该记录，且不会产生第二个文档。
- Elasticsearch 暂时失败时，Kafka 偏移量保持未提交，并在恢复后成功处理。
- HTTP 429/5xx 分类和退避绝不会提前确认源记录。
- 批量写入部分失败时，不得将分区偏移量推进到失败项之后。
- 毒消息进入 `logs.dlq` 后，下一条有效记录可以继续处理。
- 死信队列写入失败时，源偏移量保持未提交。
- 处理器终止时，不会提交超过未完成任务的偏移量。
