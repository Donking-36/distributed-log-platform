# ADR-002: At-least-once delivery and idempotent Elasticsearch writes

- Status: Accepted
- Date: 2026-07-30

## Context

Filebeat and Kafka consumer recovery can redeliver events. Elasticsearch writes
can also succeed while the client loses the response. Therefore observing no
duplicates in one test cannot justify an exactly-once claim.

The processor needs deterministic identity, explicit acknowledgement boundaries
and a poison-message path so that recovery neither creates duplicate documents
nor blocks a partition forever.

## Decision

### Delivery guarantee

The pipeline is **at least once**. It does not claim unrestricted exactly-once
delivery. Correctness is measured as unique logical inputs versus unique
Elasticsearch documents inside a declared test window and resource boundary.

### Deterministic event ID

`event_id` version 1 uses these fields in this exact order:

1. `kubernetes.pod.uid`
2. `container.id`
3. `log.file.path`
4. `log.offset` as base-10 text
5. `@timestamp` normalized to UTC RFC3339Nano
6. raw `message`

Encode UTF-8 values as a version prefix followed by length-prefixed fields:

```text
v1|<byte-length>:<value><byte-length>:<value>...
```

Compute SHA-256 over those bytes and render:

```text
sha256:<lowercase-hex>
```

Length prefixes prevent separators inside values from changing field
boundaries. Missing required identity fields are permanent validation errors;
the processor must not invent random replacements.

### Elasticsearch write

- Write the computed value into the document `event_id` field and use the same
  value as Elasticsearch document `_id`.
- Use bulk `create`, not `index` or an autogenerated ID.
- Treat a successful create as processed.
- Treat a bulk item-level HTTP 409 for the same `_id` as a confirmed duplicate,
  increment a duplicate counter and consider the record processed.
- Handle bulk item results individually; one failed item cannot be hidden by a
  successful HTTP response for the batch.

### Kafka acknowledgement

- Filebeat's producer acknowledgement from Kafka and `log-processor` consumer
  offset commits are separate boundaries. Neither producer nor consumer uses a
  fire-and-forget success assumption.
- Filebeat business-topic writes and processor DLQ writes require Kafka broker
  acknowledgement equivalent to `acks=all`. With replication factor one this
  confirms only the local broker and is not a high-availability guarantee.
- Disable automatic offset commits.
- A record becomes committable only after:
  1. Elasticsearch created it;
  2. Elasticsearch confirmed it already exists with HTTP 409; or
  3. its permanent failure was successfully written to the accepted DLQ path.
- Commit only the highest contiguous processed offset per partition. Do not
  commit past an earlier unresolved record.
- On rebalance or crash, unfinished offsets remain uncommitted and may be
  redelivered.
- On graceful shutdown, stop fetching, finish or cancel bounded in-flight work,
  commit only completed contiguous offsets, then exit.

### Retry classification

Retry without committing on network timeouts and transient Elasticsearch
responses such as 429, 502, 503 and 504. One delivery cycle permits at most six
attempts, starting at 250 ms, doubling to a 4 s cap with full jitter;
cancellation must interrupt the wait.

An exhausted delivery cycle must not discard, DLQ or acknowledge the record.
Pause the affected partition, expose an unready state and leave the offset for
recovery or redelivery. A new delivery cycle starts only after the dependency
health check recovers or the processor restarts. A request whose response was
lost is safe to retry with `create`; if the first request succeeded, the retry
converges through HTTP 409.

Authentication/authorization failure is a configuration failure and makes the
processor unready. Missing templates, conflicting mappings and cluster blocks
are also systemic failures: stop progress and do not commit. Invalid JSON,
missing required fields and an isolated record value that violates an already
verified mapping are permanent record failures.

### Poison messages

The initial permanent-failure path is Kafka topic `logs.dlq`, one partition and
replication factor one. A DLQ record includes:

- original source topic, partition and offset;
- error class and safe error summary;
- attempt count;
- `test_run_id` when present;
- original payload subject to the same local-data and secret rules.

The source offset is committable only after the DLQ write succeeds. If the DLQ
write fails, the source record remains unresolved. The normal business consumer
does not subscribe to `logs.dlq`.

## Consequences

### Positive

- Redelivery converges on one Elasticsearch document.
- Offset progress reflects a durable result or durable failure evidence.
- Partial bulk failures and poison messages are observable.
- The event ID algorithm is independently unit-testable and versioned.

### Negative

- A transient Elasticsearch outage can pause progress for a partition.
- DLQ operation and retention add configuration and test work.
- Changing identity fields or encoding requires a new ID version and migration
  decision.
- At-least-once Kafka traffic may still contain duplicate physical records.

## Rejected alternatives

- **Elasticsearch autogenerated IDs:** duplicates documents on redelivery.
- **Random UUID at processing time:** the same source event gets a different ID
  after retry.
- **Commit Kafka before Elasticsearch:** can lose events after a processor
  crash.
- **Infinite retry for every error:** one invalid event can block a partition
  forever.
- **Treat every failure as DLQ:** hides infrastructure outages as bad data.
- **Claim exactly once:** unsupported across Filebeat, Kafka and Elasticsearch
  failure boundaries.

## Validation obligations

- The same canonical input always produces the same `event_id`.
- Every identity-field change produces a different ID.
- Field values containing separators do not collide.
- Duplicate delivery produces one Elasticsearch document and one duplicate
  observation.
- Elasticsearch success followed by a lost response or lost commit is retried;
  HTTP 409 then closes the record without a second document.
- A transient Elasticsearch failure leaves the Kafka offset uncommitted and
  succeeds after recovery.
- HTTP 429/5xx classification and backoff never acknowledge the source record
  early.
- A partial bulk failure cannot advance a partition offset past the failed
  item.
- A poison event reaches `logs.dlq`; the next valid record can proceed.
- A failed DLQ write leaves the source offset uncommitted.
- Processor termination commits no offset beyond unfinished work.
